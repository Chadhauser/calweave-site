“Exceeded maximum execution time”: why your calendar sync script dies, and what actually fixes it

You wrote (or copied) an Apps Script that reads Google Calendar™ events into a Google Sheet™. It worked on a test week, then you pointed it at the real calendar and it stopped partway with “Exceeded maximum execution time”. Nothing is broken — you've hit a hard platform limit, and it needs an architectural fix, not a retry.

What the error actually means

Google Apps Script kills any single run after 6 minutes on consumer and most Workspace accounts (30 minutes on some enterprise tiers). Calendar work hits this fast because CalendarApp.getEvents() over a long date range returns thousands of event objects, and every property you read — guests especially — is its own slow call. A year of a busy calendar is often simply more than six minutes of work.

The three genuine code fixes

  1. Slice the date range. Sync month by month, writing each batch before moving on. Simple, but you must track which slice you've reached.
  2. Checkpoint and resume with triggers. Before the 6-minute wall, save your position with PropertiesService, schedule a one-off trigger with ScriptApp.newTrigger(...).timeBased().after(60*1000), and exit cleanly; the next run resumes at the checkpoint. This is the canonical pattern — and now your script needs state management, duplicate protection, and cleanup of orphaned triggers.
  3. Cut the per-event work. Fetch with the Advanced Calendar Service (the Calendar API via Calendar.Events.list) instead of CalendarApp — it returns plain objects in pages of up to 2,500 and is dramatically faster — and write rows with one setValues() per batch, never cell by cell.

All three work. Together they turn a 40-line script into a few hundred lines with state, and every re-run now needs duplicate handling: if the script died mid-write last time, which rows are already in the sheet?
